Overview

This assignment was about representing and editing geometry, first as Bezier curves and surfaces and then as triangle meshes. Section I uses de Casteljau's algorithm. A Bezier curve is built by repeatedly linearly interpolating neighboring control points until one point is left, and a Bezier surface does that same 1D process twice (once in u, once in v) on a grid of control points. Section II switches to the half-edge data structure. I implemented area-weighted vertex normals for Phong shading, then two local mesh edits: an edge flip (which just rewires the shared diagonal of two triangles) and an edge split (which inserts a midpoint and turns those two triangles into four). Those two operations are then used for Loop subdivision, which upsamples a mesh by splitting every original edge, flipping the new edges that connect an old vertex to a new midpoint, and moving vertices with Loop's weighted averages so the surface gets smoother.

Section I: Bezier Curves and Surfaces

Part 1: Bezier Curves with 1D de Casteljau Subdivision

A Bezier curve is a parametric curve \(x(t)\), \(t \in [0, 1]\) that is defined by various control points. It passes through the first and last control points. The other points are called handles, and they are basically directional control lines that help direct the path of the curve. de Casteljau’s algorithm is a method to construct a Bezier curve. It evaluates \(x(t)\) by repeated linear interpolation on the points that define the curve. Each step replaces every adjacent pair with \((1 - t)\, b_i + t\, b_{i+1}\), which is basically the linear interpolation of every pair of neighboring points,so each level has one fewer point. The last remaining point is \(x(t)\) (a point along the curve). A Bezier curve is the path traced by the last point of de Casteljau as \(t\) runs from 0 to 1. One run of the algorithm gives one point. The curve is all of those points.

In terms of the implementation, the BezierCurve::evaluateStep function is responsible for performing single step of the algorithm. This means that we start with N control points, perform a step, and are left with N-1 points (that is what makes up a single step). The implementation performs N-1 linear interpolations to produce N-1 new points, and then returns those as a vector. The rest of the code calls this function once per level, and so pressing E will show one row of the de Casteljau pyramid at a time.

The implementation is tested on the below example, a curve defined by 6 control points. It takes five steps to reach the final red point. The green curve shows the result of the same evaluation using at many values of \(t\) between 0 and 1. Scrolling changes the \(t\) value used in the blue display points. Part 2: Bezier Surfaces with Separable 1D de Casteljau

de Casteljau's algorithm extends from curves to surfaces by applying the same interpolation process in two directions. This means a Bezier surface extends the curve to two parameters, \(u\) and \(v\), both in \([0, 1]\). The input is a grid of control points (rather than a "line" of them). In this assignment each patch is \(4 \times 4\), so each row is itself a Bezier curve parameterized by \(u\). de Casteljau is still an algorithm for evaluating a 1D curve. In order to apply this to a surface, the separable evaluation approach performs it two times. First, evaluate every row at the same \(u\). That produces one point per row, and those points can then become the control points of a moving curve. Then, that moving curve is evaluated at \(v\). The last point is the surface point \(x(u, v)\).

In terms of the implementation of this extension, there were 3 different functions that made it up. BezierPatch::evaluateStep is the same one-level linear interp implementation as the Bezier curve function, but the points are now in 3D and \(t\) is an argument, since a surface uses the step once at \(u\) and once at \(v\) (so that value needs to be parameterized). evaluate1D repeats that evaluateStep operation until just one point is left. The curve viewer stops after one level so that E can show each row of the pyramid. A surface only needs the final point, which is what this function returns. evaluate(u, v) calls evaluate1D on every row at \(u\), then calls evaluate1D on those points at \(v\). Section II: Triangle Meshes and Half-Edge Data Structure

Part 3: Area-weighted vertex normals

The normal vector is defined as the arrow pointing straight out of the surface. This is what controls lighting, because the surface appears bright whenever the arrow is pointing toward the light, and dark where it points away from it. Flat shading just uses the normal for the whole triangle (which is that triangle's normal). Each face becomes one single flat shade. The result is an image that looks faceted (like the one on the left below). By contrast, phong shading tries to get around this by blending across the triangle surface. It stores a normal at each vertex, then uses vertex normals to blend across and achieve smoother shade changes. This part has the implementation for getting those vertex normals.

Vertex::normal builds the normal for a vertex (since normals are defined for the triangles/surfaces). Each vertex is touched by a bunch of triangles that sit in a fan. The half-edge loop will visit them all. It starts at one half-edge leaving the vertex, then twin()->next() steps to the next triangle. We continue looping across the entire fan until the loop returns to the starting triangle. For each triangle (check that this isn't some boundary just to be sure), we get the vectors from the other two corners at \(p_1\) and \(p_2\) and the original current vertex \(p_0\). Note that boundary faces are skipped because those are the fake polygon around a hole rather than a triangle. We then take the cross product of this: cross\((p_1 - p_0,\, p_2 - p_0)\). That vector points out of the triangle being looked at. The sum of these normals for each adjacent/touching triangle is then scaled to length 1 with unit(). This becomes the vertex vector.

Part 4: Edge flip

The goal of this part was to perform an edge flip for a pair of triangles. What this does is change the diagonal that a pair of triangles sharing an edge uses (switch to the other diagonal edge as the shared edge). So, two triangles ABC and BCD that share an edge BC then become 2 triangles that share the other diagonal edge AD. The four outer edges and vertices (A, B, C, D) stay where they are. Only the internal connections to form the internal diagonal edge between those vertices change.

The implementation for this function is in HalfedgeMesh::flipEdge, where it is done by reassigning a bunch of pointers. No vertices, edges, faces, or half-edges are created or deleted (consistent with what we outlined below). It really boils down to a bunch of reassigning. The two half-edges on the shared edge need to be flipped. Before, the edge and its twin used to be b->c and c->b. After performing the edge flip, they should be a->d and d->a. The 4 outer edges have to keep their start vertices, so those stay the same. But, the triangles themselves are rebuilt, so the next pointers should be updated to now reflect the new triangles split by the new diagonal. Each vertex, face, and edge is then pointed at a half-edge that still belongs to it. A vertex that kept pointing at the old shared edge would be pointing at a half-edge that now starts somewhere else. Finally, we account for the edge case of getting a boundary edge at the start. This should be returned as is, because it has only one triangle and there is no opposite corner that we could even flip to. All of the original pointers are saved before any call to setNeighbors, since that call overwrites them.

The biggest thing that was hard to debug was making sure to save original pointers and references before calling setNeighbors, as that is a mutating call. At first, I forgot that a call to that function would overwrite next, twin, vertex, edge, and face (especially twin). I had initially made the mistake of forgetting to save references to the twins, which led to bugs in my implementation. I had to move all the setNeighbors calls to be together at the end of the function. The other bug showed up after the half-edges themselves were correct. Vertex b was still storing h0 as its half-edge, but the flip changes h0 from b → c into a → d, so it no longer starts at b. The next walk around b followed a half-edge into the wrong triangle and the mesh broke on a second flip. Each vertex had to be pointed at a half-edge that still starts there: b at h4 (b → d) and c at h1 (c → a). Upon fixing this, the flips worked as expected.

Part 5: Edge split

An edge split basically takes a shared edge and splits/divides it into 2. Then, it adds the other 2 diagonal connections. This turns the 2 trianges into 4 triangles. To be more precise, recall that triangles ABC and BCD share edge BC. Then, we add a new vertex m at the midpoint of BC. We can then split BC into Bm and mC. We also draw new edges from m to opposite corners A and D, forming Am and mD. The four outer edges stay where they are, as they are unchanged by the addition of m.

The implementation for this operation is in HalfedgeMesh::splitEdge. It starts very similar to the edge flips, where we extract the same half edges, and from those the vertices, edges, faces, and twins (to avoid the same mistake as last time with setNeighbors). Then, unlike a flip, there are new things being produced. While a flip was 2 triangles -> 2 new triangles, a split makes 4 triangles. This means there is 1 new vertex (m), 3 new edges (one can be reused), 2 new faces (for 2 new triangles), and 6 half-edges (because each edge needs a half-edge in each direction). setNeighbors then builds the four triangles one by one: b->m->a->b, m->c->a->m, m->d->b->m, and c->m->d->c. The new vertex's half-edge is set to m->b, which lies on the edge that was split. The two new lines are marked as new. Both pieces of the original edge are marked as not new. Once again, boundary edges are ignored at the start.

Something that I found helpful for debugging this part was drawing stuff out one by one. Especially because we were adding new things, each time I did an operation, I re-updated my diagram to keep the pointers and associated variables up to date. This helped me catch bugs much easier than part 4. I was also able to avoid the same setNeighbor issue as last time by working iteratively: update diagram -> write code to reflect that update -> back to diagram (in a loop).

Part 6: Loop subdivision for mesh upsampling

The final part of this is to implement loop subdivision, which upsamples a mesh. Each run of this will replace every triangle with four smaller ones (from those triangle's edges) and the move the vertices so the surface gets smoother. The new vertices are not plain midpoints along them, and the old vertices also do not have to stay in their old position. Both are moved by a weighted average of their neighbors. That averaging is what helps get rid of the sharp corners and achieve a more round shape.

The implementation of each step of this upsampling logic is in MeshResampler::upsample. The first thing we do is compute the new position from the original mesh. We then store these new positions, but this needs to be done before the edges are actually split. This is because new positions need to be computed from the original mesh before any vertices are moved. Otherwise, the calculations would be using changing values and thus be wrong.

For each old vertex, we can get n = degree = the number of triangles that touch it. We can set the weight on the neighbors as u. Based on the lecture, we know that n = 3 => u = 3/16, and n != 3 => u = 3 / (8n). The explanaiton for this is that if n is small, it should get a bigger u. This means that a vertex is more influenced by the neighbors (and vice-versa). We do the same walk as whatever we used for the vertex normal. The neighbor across each edge is h->twin()->vertex (twin flips the edge, vertex gets the other vertex than the one we are currently looking at). The stored position is then the weighted sum of the current position and the sum of the neighbor positions.

For each edge, the new point uses the two endpoints and the two opposite corners. The position that we store becomes 3/8(b+c) + 1/8(a+d). The endpoints (b and c) count more than the opposite corners, which is why it has higher weightage. As a result, the new point stays near the middle of the edge and only slides a little toward the new endpoints (a and d).

The next is to split edges, but only the original ones. We iterate through all the edges (note: one bug that I realized is that I have to save nEdges() before the loop since its actively being modified). I also had to use the edge iterator from before the call to splitEdge -- another tricky realization. This is because slitEdge will insert new edges. So, we need to work with the original set. splitEdge puts the new vertex m at the midpoint and b and c. We replace this with the weighted position for that edge. We also keep isNew up to date for the edges. This is so that whenever that value is used in the algorithm is used, it is reliable.

The flips turn the splits into Loop's pattern. After the splits, each triangle has new edges going from the midpoints to the old corners. However, those edges are going wrong way. They therefore need to be flipped. We only do this to new edges though. Another bug that was found is that the endpoints should not both be new or both be old (exactly one should be new). This was debugged by looking at the funky diagonal patterns that emerged when I did not do this processing properly (the GUI tells the information, and I used that debug the implementation). The other edges for which this doesn't apply will stay unchanged. Finally, the originally calculated newPosition from the beginning is then applied to every vertex. Those positions were computed up front, but they just need to be applied now.

Teapot results: as we upsample more and more, the body, lid, spout, and handle (the components of the teapot) generally keep their shape. However, the sharp creases round up as more and more upsampling is done. This is most apparent by the lip of the lid and the tip of the spout, as those are some of the more rounded parts of the pot. The results also include close-up views so its a bit easier to see. Without upsampling, the spout starts as a few big triangles with a sharp tip. After two iterations, the tip is much rounded and the surface is a dense mesh.

Cube results: this is the view of a cube whose faces are already split into two triangles. A corner that a diagonal touches sits in both triangles of that face. A corner the diagonal misses sits in only one. Since every corner meets three faces, the eight corners do not all have the same degree. The weight directly depends on that degree. When n=3, it gets pulled harder, but otherwise it stays closer to where it was. After a few iterations the cube gets smoother, but it rounds unevenly and the faces go lopsided.

Splitting edges before any step changes those degrees. This time, when the cube launched, I split each of the 12 outlined edges once. I did not split the face diagonals. Every outline edge then has a vertex in its middle, and each corner is now next to those nearby midpoints instead of only to the far corners of the cube. Splitting the three edges that meet at a corner also adds triangles around it, so its degree goes up, making the weight smaller. This means the corner is not pulled as far. Three Loop steps after that stay closer to a rounded box. The corners are sharper, and the result ends up being a bit more even.

Splitting only the three edges that meet at one corner does the same thing in one place. That corner's degree goes up and its neighbors are now close midpoints, so it stays pointier. The other corners still round off the normal way.
